## 知识检查与教学

### 知识点一：文件持久化历史的完整责任链

#### 问题

当 `conversation_chain.invoke()` 被调用时，从 `session_id` 到历史文件的“读取 → 注入 Prompt → 模型调用 → 回写文件”分别由哪些对象或函数负责？模型本身是否知道历史文件的存在，为什么程序重启后同一会话仍可能恢复历史？

#### 我的原始回答

> conversation_chain获取session_id后，先完成FileChatMessageHistory的初始化，再调用messages方法取得历史会话记录，再把input和chat_history注入到ChatPromptTemplate中，ChatPromptTemplate注入完成后传给llm，由llm进行本次会话输出，输出好的内容，conversation_chain最后调用add_messages方法把新一轮的会话记录添加到文件中。模型本身不知道这个历史文件存在，因为文件不会随着程序重启而消失，程序重启后session_id不变，还是能访问到之前的历史文件，也就是历史会话记录

#### 提示 / 教学过程

- 回答已经正确覆盖 `session_id → get_history() → FileChatMessageHistory → messages → Prompt → LLM → add_messages() → 文件` 的主要链路。
- 补充精确边界：模型不知道文件存在，是因为它只接收应用组装后的消息；读取、注入和写回都是应用层行为。
- 不需要提示或重新回答。

#### 我的重新回答

无需重新回答；首次回答已证明核心理解。

#### 评价

能够独立解释文件历史的读取、注入和回写，并正确说明相同 `session_id` 可在进程重启后重新定位持久化文件。

#### 正确理解

`RunnableWithMessageHistory` 根据 `session_id` 调用 `get_history()` 取得历史对象；该对象的 `messages` 属性读取并反序列化文件内容；包装器将历史和当前输入交给 Prompt，LLM 只看到最终消息；调用结束后包装器通过 `add_messages()` 把本轮 Human/AI 消息写回。持久化来自应用文件，而不是模型记忆。

### 知识点二：Loader、Document 与 RAG

#### 问题

`CSVLoader` 或 `JSONLoader` 为什么返回 `Document` 而不是只返回普通字符串？分别说明 `page_content`、`metadata` 在 RAG 中的作用，以及 `jq_schema` 选择范围过大或过小时对检索的影响。

#### 我的原始回答

> document是内容+内容来源
> 1、Document.page_content保存的是内容，Document.metadata保存的是数据源(来自哪个文件，第几行...)
> 2、RAG检索中Document.page_content用来计算向量相似度，Document.metadata提供数据来源，确保数据不是模型瞎编的，实现有依据
> 3、jq_schema的范围过大，会导致噪声过多，回答的精度下降，范围过下，会导致失去大量的上下文信息，回答的召回率下降

#### 提示 / 教学过程

- 回答正确区分了正文和来源信息，也能把 `jq_schema` 范围联系到检索噪声与上下文缺失。
- 补充：`metadata` 可以用于过滤、追踪、引用和调试，但它本身不能确保模型不产生幻觉；仍需正确注入检索正文、约束回答并核对证据。
- 不需要提示或重新回答。

#### 我的重新回答

无需重新回答；首次回答已覆盖核心机制。

#### 评价

能够将 Loader 返回的数据结构连接到 RAG 的 Embedding、检索和来源追踪，不只是记住 API 参数。

#### 正确理解

`page_content` 是后续切分、Embedding 和检索的正文；`metadata` 是来源、行号等辅助信息，可用于过滤、引用和调试。`jq_schema` 过宽会引入无关信息或形成过粗文档，过窄会丢失回答所需上下文。

### 知识点三：会话隔离的简单迁移

#### 问题

线上系统中两个真实用户错误地使用同一个 `session_id="user_001"` 会出现什么问题？结合 `FileChatMessageHistory` 说明原因，并设计避免不同用户历史互相污染的会话标识。

#### 我的原始回答

> 1、出现会话记录污染，可能造成隐私泄露
> 2、因为add_messages和messages都是通过session_id进行操作的，所以两个用户使用同一个session_id就会同时使用一份历史会话记录文件
> 3、感觉可以采用(session_id,conversation_id)的形式，首先每个人的session_id不同，一个人也有可能有多个conversation，所以要有多个conversation_id

#### 提示 / 教学过程

- 首次回答已正确识别会话污染、隐私风险和共享文件的直接原因。
- 补充命名建议：线上通常用经过认证的 `user_id` 与不可预测、全局唯一的 `conversation_id` 组成存储键，并在读取时校验该会话属于当前用户。
- 不需要提示或重新回答。

#### 我的重新回答

无需重新回答；首次回答已完成简单迁移。

#### 评价

能够把本地 `session_id` 文件映射迁移到多用户线上场景，识别隐私风险，并提出用户与会话双层隔离方案。

#### 正确理解

若两个用户共享同一存储键，`messages` 和 `add_messages()` 会读写同一份历史，造成上下文串线和隐私泄露。应使用 `user_id + conversation_id` 确定会话，并校验所有权；仅依赖客户端任意传入的简单字符串并不足够安全。
